A one-page revision sheet for the night before (or the hour before) a design interview. Every entry links back to the lesson that explains it in depth.

## The interview flow

| Step | Time (45 min) | Deliverable |
| --- | --- | --- |
| Requirements | 5–7 min | 3–4 functional, key non-functional (scale, latency, consistency, durability), out of scope |
| Estimation | 3–5 min | QPS (read/write), storage, bandwidth — each ending with "so…" |
| API | 3–5 min | Core endpoints, pagination, idempotency |
| Data model | 3–5 min | Entities, keys, store choice with a reason |
| High-level design | 10–12 min | End-to-end diagram covering every functional requirement |
| Deep dives | 10–15 min | The 2–3 hardest parts; failure modes |

Decision template: **requirement → options → choice → cost**. ([Framework](/system-design/hld/hld-interview-framework))

## Choosing storage

| Need | Choose |
| --- | --- |
| Transactions, relationships, ad-hoc queries | PostgreSQL / MySQL |
| Key lookups, very low latency, counters, sessions | Redis / DynamoDB |
| Massive write throughput, time-ordered per key | Cassandra / ScyllaDB / Bigtable |
| Flexible documents read as a whole | MongoDB / DynamoDB |
| Multi-hop relationships | Graph DB (or sharded SQL + cache at scale) |
| Full-text search, facets | Elasticsearch / OpenSearch |
| Files, images, video | Object storage + CDN |
| Analytics over billions of rows | Columnar warehouse / OLAP (BigQuery, ClickHouse, Druid) |
| Global strong consistency + SQL | Spanner / CockroachDB / YugabyteDB |

([SQL vs NoSQL](/system-design/hld/sql-vs-nosql), [Blob Storage](/system-design/hld/blob-storage), [Batch & Stream](/system-design/hld/batch-and-stream-processing))

## Scaling data

| Technique | Use when | Watch out for |
| --- | --- | --- |
| Index | Slow queries on a column | Write overhead; composite column order |
| Cache (cache-aside + TTL) | Read-heavy, skewed access | Invalidation races, stampedes, hot keys |
| Read replicas | Read throughput | Replication lag → read-your-writes |
| Sharding | Writes or data beyond one node | Shard key choice, hot partitions, cross-shard queries |
| Consistent hashing | Nodes join/leave | Use virtual nodes |
| CDN | Static/public content, global users | Cache keys, never cache personalised responses |

## Consistency cheat sheet

| Concept | One-liner |
| --- | --- |
| CAP | During a partition, choose consistency or availability |
| PACELC | Else (normally), choose latency or consistency |
| Linearizable | Acts like a single copy in real time — locks, uniqueness, balances |
| Causal | Cause before effect for everyone; available under partition |
| Read-your-writes | Authors see their own changes — route to primary briefly |
| Eventual | Converges eventually — feeds, counters, caches |
| Quorum | W + R > N → read overlaps latest write (usually) |
| Isolation | Read Committed default; only Serializable stops write skew |

([CAP](/system-design/hld/cap-and-pacelc), [Consistency](/system-design/hld/consistency-models), [Transactions](/system-design/hld/transactions-and-isolation))

## Communication

| Need | Use |
| --- | --- |
| Public CRUD API | REST + cursor pagination + idempotency keys |
| Internal low-latency calls | gRPC |
| Flexible client-driven fetching | GraphQL / BFF |
| Server → client stream | SSE |
| Bidirectional real-time | WebSockets |
| Background tasks, one consumer each | Queue (SQS, RabbitMQ) |
| Events for many consumers, replay | Log (Kafka) — order per partition key |
| Reliable "write DB + publish event" | Transactional outbox / CDC |
| Multi-service workflow | Saga (orchestrated), idempotent steps, compensations |

## Reliability toolkit

- **Redundancy** across AZs; no single points of failure (LB pairs, replicas, multi-AZ).
- **Timeouts** on every call; **retries** only for idempotent ops, with exponential backoff + jitter, at one layer.
- **Circuit breakers**, **bulkheads**, **load shedding**, **graceful degradation**.
- **Rate limiting**: token bucket (bursts OK) or sliding window counter; Redis + Lua for distributed; fail open vs closed per rule.
- **Leases + fencing tokens** for single-writer guarantees.
- **SLOs** and burn-rate alerts; golden signals; trace IDs across hops.

## Final-minute checklist

Requirements confirmed · numbers drive decisions · every functional requirement has a path through the diagram · consistency chosen per data type · no single point of failure · retries are idempotent · hot keys handled · failure walk-through done · observability and security mentioned · trade-offs stated out loud.

## Practice

Write your answer before opening the suggested one. If you mark it "Partly" or "Missed it", it comes back in your review deck.

<Practice task="You have 60 seconds left in an interview and the interviewer asks 'What would you monitor in this system?' Give a quick, structured answer you could use for almost any design.">

Use the golden signals per service, plus the business metric:

1. Latency: p50 and p99 of the main endpoints (separately for errors).
2. Traffic: requests per second, and queue depth or consumer lag for async parts.
3. Errors: error rate by type (5xx, timeouts, dependency failures).
4. Saturation: CPU, memory, connection pools, disk, and cache hit ratio.
5. The business metric that shows users are succeeding (orders per minute, messages delivered).

Alert on SLO burn rate (user-visible symptoms), not on every CPU spike, and trace requests across services to find which hop is slow.

</Practice>

<Takeaways>

- Run every design in the same order: requirements → estimates → API → data model → high-level design → deep dives → wrap-up.
- Let numbers drive decisions: a day is about 10^5 seconds, 1M requests a day is about 12 QPS, and you always size for peak.
- Choose storage and consistency per data type; money and locks lean strongly consistent, feeds and counters can be eventual.
- Scale reads with caches and replicas, writes with sharding and queues; remove single points of failure and make retries idempotent.
- Finish with failures, hot keys, observability, security and the trade-offs you made, said out loud.

</Takeaways>
