Many LLD rounds end with "now show me the tables" — and some (Amazon, Flipkart, fintechs) ask for the schema up front. The interviewer wants three things: a **faithful mapping** of your class model to tables, **constraints that enforce the invariants** your code relies on (so a bug or a race can't corrupt data), and **indexes derived from the queries** you'll run. This lesson covers the mapping rules, then works through the schemas behind the case studies. Every DDL statement and query here is run against PostgreSQL 15 in the course's verification suite, with a test that each constraint really rejects the bad write it exists to stop.

## 1. Mapping classes to tables

| Class model | Table design |
| --- | --- |
| Entity (`Booking`, `Account`) | A table with a surrogate primary key (`BIGSERIAL`) |
| Value object (`Money`, `DateRange`, `Address`) | Columns embedded in the owner's table (`amount_paise`, `stay DATERANGE`) |
| Enum (`BookingStatus`) | `TEXT` with a `CHECK (status IN (...))`, or a lookup table if values carry data |
| Association, many-to-one | Foreign key on the "many" side (`booking.show_id`) |
| Many-to-many | Join table with a composite primary key (`expense_split (expense_id, user_id)`) |
| Composition (part dies with whole) | Foreign key with `ON DELETE CASCADE` (`seat.screen_id`) |
| Aggregation (part outlives whole) | Plain foreign key, often nullable; no cascade |
| Inheritance | See the three strategies in section 6 |

Two habits that interviewers notice:

- **Money as integers** (`BIGINT` paise) or `NUMERIC(19,2)` — never `FLOAT`.
- **Timestamps with time zone** (`TIMESTAMPTZ`) for instants; `DATE` only for calendar dates such as a hotel stay.

## 2. Invariants belong in constraints

Your Java code checks "a seat can't be booked twice". But two servers, a retried request or a future bug can all bypass that check. **The database is the last line of defence**, and constraints are how you tell it the rules:

| Invariant | Constraint |
| --- | --- |
| A value is never negative | `CHECK (balance_paise >= 0)` |
| A status implies certain columns | `CHECK ((status = 'HELD') = (held_by IS NOT NULL AND hold_expires_at IS NOT NULL))` |
| One of something | `UNIQUE (...)` or a composite primary key |
| One *active* something | Partial unique index: `UNIQUE ... WHERE exit_at IS NULL` |
| No overlapping ranges | Exclusion constraint: `EXCLUDE USING gist (room_id WITH =, stay WITH &&)` |
| A request is processed once | `UNIQUE (idempotency_key)` |
| Relationships are valid | Foreign keys |

The "status implies columns" pattern is worth memorising: it makes illegal states unrepresentable at the database level, the same goal as making them unrepresentable in your classes.

## 3. Movie booking: the unit of contention is (show, seat)

```sql
CREATE TABLE seat (
    id        BIGSERIAL PRIMARY KEY,
    screen_id BIGINT NOT NULL REFERENCES screen(id) ON DELETE CASCADE,   -- composition
    row_label TEXT   NOT NULL,
    seat_no   INT    NOT NULL,
    seat_type TEXT   NOT NULL CHECK (seat_type IN ('REGULAR', 'PREMIUM', 'RECLINER')),
    UNIQUE (screen_id, row_label, seat_no)
);

CREATE TABLE show (
    id        BIGSERIAL PRIMARY KEY,
    movie_id  BIGINT      NOT NULL REFERENCES movie(id),
    screen_id BIGINT      NOT NULL REFERENCES screen(id),
    starts_at TIMESTAMPTZ NOT NULL
);
CREATE INDEX show_by_movie_and_time ON show (movie_id, starts_at);      -- "shows of this movie from today"

CREATE TABLE show_seat (                                                 -- one row per seat per show
    show_id         BIGINT NOT NULL REFERENCES show(id) ON DELETE CASCADE,
    seat_id         BIGINT NOT NULL REFERENCES seat(id),
    status          TEXT   NOT NULL DEFAULT 'AVAILABLE' CHECK (status IN ('AVAILABLE', 'HELD', 'BOOKED')),
    held_by         BIGINT,
    hold_expires_at TIMESTAMPTZ,
    booking_id      BIGINT REFERENCES booking(id),
    price_paise     BIGINT NOT NULL CHECK (price_paise >= 0),
    version         INT    NOT NULL DEFAULT 0,
    PRIMARY KEY (show_id, seat_id),
    CHECK ((status = 'HELD')   = (held_by IS NOT NULL AND hold_expires_at IS NOT NULL)),
    CHECK ((status = 'BOOKED') = (booking_id IS NOT NULL))
);
```

The same split as the class model: `seat` is the physical seat (never changes); `show_seat` is its availability **for one show**. When a show is created, insert one `show_seat` row per seat.

**Holding seats is a single conditional `UPDATE`** — the database equivalent of compare-and-set:

```sql
UPDATE show_seat
   SET status = 'HELD', held_by = :user, hold_expires_at = now() + interval '5 minutes', version = version + 1
 WHERE show_id = :show AND seat_id IN (:seats)
   AND (status = 'AVAILABLE' OR (status = 'HELD' AND hold_expires_at < now()));
-- rows changed must equal the number of seats requested; otherwise ROLLBACK (all or nothing)
```

Row locks taken by the `UPDATE` serialise concurrent holds on the same seats; the `WHERE` re-checks the status after waiting, so the second request finds the seat taken and changes zero rows. Confirmation is another conditional update: `... SET status = 'BOOKED' WHERE status = 'HELD' AND held_by = :user AND hold_expires_at > now()` — zero rows means the hold was lost.

## 4. "One active X": partial unique indexes

A parking spot can have many tickets over time but only **one open** ticket; a plate can't be parked twice at once:

```sql
CREATE TABLE parking_ticket (
    id        BIGSERIAL PRIMARY KEY,
    spot_id   BIGINT      NOT NULL REFERENCES parking_spot(id),
    plate     TEXT        NOT NULL,
    entry_at  TIMESTAMPTZ NOT NULL,
    exit_at   TIMESTAMPTZ,
    fee_paise BIGINT,
    CHECK (exit_at IS NULL OR exit_at >= entry_at),
    CHECK ((exit_at IS NULL) = (fee_paise IS NULL))
);
CREATE UNIQUE INDEX one_active_ticket_per_spot  ON parking_ticket (spot_id) WHERE exit_at IS NULL;
CREATE UNIQUE INDEX one_active_ticket_per_plate ON parking_ticket (plate)   WHERE exit_at IS NULL;
```

Two gates inserting a ticket for the same spot at the same moment: one insert wins, the other gets a unique violation — the double assignment is impossible even if the application's lock is wrong. (MySQL has no partial indexes; emulate with a generated column that is `spot_id` when active and `NULL` otherwise, plus a unique index on it.)

## 5. Ranges that must not overlap: exclusion constraints

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE room_booking (
    id       BIGSERIAL PRIMARY KEY,
    room_id  BIGINT    NOT NULL REFERENCES room(id),
    guest_id BIGINT    NOT NULL,
    stay     DATERANGE NOT NULL CHECK (lower(stay) < upper(stay)),   -- '[2026-10-10,2026-10-12)'
    status   TEXT      NOT NULL CHECK (status IN ('CONFIRMED', 'CANCELLED')),
    EXCLUDE USING gist (room_id WITH =, stay WITH &&) WHERE (status = 'CONFIRMED')
);
```

"No two confirmed bookings for the same room have overlapping stays" is exactly one constraint. `DATERANGE` is half-open by default, so a checkout and a check-in on the same day don't conflict. Finding free rooms is the same operator:

```sql
SELECT r.number FROM room r
 WHERE r.type = 'DELUXE'
   AND NOT EXISTS (SELECT 1 FROM room_booking b
                    WHERE b.room_id = r.id AND b.status = 'CONFIRMED'
                      AND b.stay && daterange(:check_in, :check_out));
```

Without range types (MySQL), the portable alternative is **one row per room per night** with `UNIQUE (room_id, night)` — more rows, but a plain unique index does the job.

## 6. Inheritance: three strategies

`PaymentMethod` with subtypes `Card` and `Upi`:

| Strategy | Tables | Pros | Cons |
| --- | --- | --- | --- |
| **Single table** | One table + `type` column; subtype columns nullable | Simple queries, no joins, polymorphic lists are trivial | Nullable columns; need CHECKs to keep rows consistent |
| **Table per subtype** (joined) | Base table + one table per subtype sharing the key | Normalised; NOT NULL possible | Joins on every read |
| **Table per concrete class** | Separate full tables | No joins for one type | "All payment methods" needs `UNION`; shared FKs are awkward |

Single table is the usual interview default when subtypes add few columns — with CHECKs that tie columns to the type:

```sql
CREATE TABLE payment_method (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT NOT NULL REFERENCES app_user(id),
    type        TEXT   NOT NULL CHECK (type IN ('CARD', 'UPI')),
    card_last4  CHAR(4),
    card_expiry DATE,
    upi_vpa     TEXT,
    CHECK ((type = 'CARD') = (card_last4 IS NOT NULL AND card_expiry IS NOT NULL)),
    CHECK ((type = 'UPI')  = (upi_vpa IS NOT NULL))
);
```

## 7. Money: ledger tables

```sql
CREATE TABLE account (
    id             BIGSERIAL PRIMARY KEY,
    owner          TEXT    NOT NULL UNIQUE,
    balance_paise  BIGINT  NOT NULL DEFAULT 0,
    allow_negative BOOLEAN NOT NULL DEFAULT false,                 -- only the bank settlement account
    CHECK (allow_negative OR balance_paise >= 0)
);

CREATE TABLE wallet_txn (
    id              BIGSERIAL PRIMARY KEY,
    idempotency_key TEXT   NOT NULL UNIQUE,
    type            TEXT   NOT NULL CHECK (type IN ('TOP_UP', 'TRANSFER', 'REFUND')),
    amount_paise    BIGINT NOT NULL CHECK (amount_paise > 0),
    reverses_txn_id BIGINT UNIQUE REFERENCES wallet_txn(id)        -- at most one refund per transaction
);

CREATE TABLE ledger_entry (
    id           BIGSERIAL PRIMARY KEY,
    txn_id       BIGINT NOT NULL REFERENCES wallet_txn(id),
    account_id   BIGINT NOT NULL REFERENCES account(id),
    amount_paise BIGINT NOT NULL CHECK (amount_paise <> 0)
);
CREATE INDEX ledger_by_account ON ledger_entry (account_id, id);
```

A transfer is one database transaction: lock both account rows **in id order** (`SELECT ... FROM account WHERE id IN (:a, :b) ORDER BY id FOR UPDATE`), insert the transaction (the unique key rejects a duplicate), insert two ledger legs, update both balances (the `CHECK` rejects an overdraft and rolls everything back). Invariants that span rows — "each transaction's legs sum to zero", "balance = sum of entries" — can't be a simple `CHECK`; verify them with reconciliation queries (or a deferred constraint trigger):

```sql
SELECT txn_id FROM ledger_entry GROUP BY txn_id HAVING sum(amount_paise) <> 0;   -- must return nothing
```

## 8. Indexes come from queries

List the queries first, then index for them:

| Query | Index |
| --- | --- |
| Shows of a movie from now on | `(movie_id, starts_at)` — equality column first, then the range column |
| Seat map of a show | Primary key `(show_id, seat_id)` already covers it |
| A wallet's statement, newest first | `(account_id, id)` |
| Active ticket for a plate | The partial unique index doubles as the lookup index |
| Expired holds to sweep | Partial index `(hold_expires_at) WHERE status = 'HELD'` |

Rules of thumb: put equality columns before range columns in a composite index; every foreign key you join or filter on usually needs an index; don't index low-cardinality columns alone (`status`) — combine them or use a partial index.

## 9. Concurrency control in the database

| Technique | SQL | Use when |
| --- | --- | --- |
| **Conditional update** | `UPDATE ... WHERE status = 'AVAILABLE'`, check rows changed | Claiming a resource (seats, coupons, spots) |
| **Optimistic locking** | `UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?` | Read-modify-write with low contention (editing a profile) |
| **Pessimistic locking** | `SELECT ... FOR UPDATE` (lock rows in a fixed order) | Multi-row invariants: transfers |
| **Constraints** | Unique, exclusion, check | The final guarantee behind all of the above |
| **Isolation level** | `SERIALIZABLE` | Complex invariants you can't express as constraints; be ready to retry |

## Interview questions

<QA q="How do you guarantee a seat can't be double-booked even if two app servers race?">
Make the database enforce it. Keep one row per (show, seat) and claim seats with a conditional UPDATE that only matches available (or expired) seats, checking that the number of rows changed equals the number requested and rolling back otherwise. Row locks serialise concurrent claims and the WHERE clause is re-evaluated after waiting, so the loser changes no rows. A CHECK tying BOOKED status to a booking id, or a unique constraint on (show, seat) in the bookings table, is the final guarantee.
</QA>

<QA q="How would you store a class hierarchy such as Card and UPI payment methods?">
Usually a single table with a type discriminator and nullable subtype columns, plus CHECK constraints that require each subtype's columns exactly when the row has that type — no joins, simple polymorphic queries. If subtypes have many columns or need NOT NULL guarantees, use a base table plus one table per subtype sharing the primary key. Table-per-concrete-class is rarely worth it because querying all methods needs UNIONs.
</QA>

<QA q="Your entity has 'only one active' semantics — one open ticket per spot, one default address per user. How do you enforce it?">
With a partial unique index that only covers active rows: UNIQUE (spot_id) WHERE exit_at IS NULL, or UNIQUE (user_id) WHERE is_default. Historical rows don't conflict, and concurrent inserts of a second active row fail. In MySQL, emulate it with a generated column that is the key when active and NULL otherwise, with a unique index on that column.
</QA>

<Practice task="Write the tables for the library system: books (titles), copies, members, loans and reservations. Which constraint guarantees a copy can't be on two active loans?">

`book (isbn PK, title, ...)`; `book_copy (barcode PK, isbn FK, status CHECK (...))`; `member (id PK, status)`; `loan (id PK, barcode FK, member_id FK, issued_on, due_on, returned_on NULL)` with a **partial unique index** `UNIQUE (barcode) WHERE returned_on IS NULL`; `reservation (id PK, isbn FK, member_id FK, created_at, status)` with `UNIQUE (isbn, member_id) WHERE status = 'WAITING'` so a member can't reserve the same title twice, and an index on `(isbn, created_at)` for FIFO order. Add `CHECK (returned_on IS NULL OR returned_on >= issued_on)`.

</Practice>

<Practice task="The coupon 'FIRST100' may be used once per user and at most 10,000 times in total. Design the tables and the redemption statement.">

`coupon (code PK, max_uses, used_count CHECK (used_count <= max_uses))` and `coupon_redemption (code FK, user_id, order_id, PRIMARY KEY (code, user_id))`. Redeem in one transaction: `UPDATE coupon SET used_count = used_count + 1 WHERE code = :c AND used_count < max_uses` (zero rows → exhausted), then `INSERT INTO coupon_redemption ...` (a primary-key violation → this user already used it; roll back the increment). The CHECK is the final guard against over-redemption.

</Practice>

<Takeaways>

- Map entities to tables, value objects to embedded columns, enums to CHECKed text, compositions to cascading foreign keys.
- Put every invariant you can into constraints: CHECK, UNIQUE, partial unique indexes, exclusion constraints, foreign keys.
- Claim contended resources with conditional UPDATEs and check the row count; lock multiple rows in a fixed order.
- Design indexes from the query list: equality columns first, then ranges.
- Verify cross-row invariants (ledgers) with reconciliation queries.

</Takeaways>
