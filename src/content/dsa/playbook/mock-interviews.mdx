Advice like "communicate clearly" is easy to agree with and hard to act on. This lesson shows what it looks like in practice. You'll read the **same problem solved by two candidates**: one weak, one strong. Both know the patterns. Only one passes. Then a third transcript shows a strong candidate **getting stuck and recovering**, which is the moment that decides most interviews.

Each transcript has the interviewer's private notes alongside and a score against the rubric from [Solving Out Loud](/dsa/playbook/interview-communication). Read the weak transcript first and try to spot every problem before you read the notes.

## The problem

> Given an integer array `nums` and an integer `k`, return the number of contiguous subarrays whose sum equals `k`.

## Transcript 1: the weak candidate

**Interviewer:** Here's the problem. *(reads it)*

**Candidate:** OK, subarrays and a sum, so that's a sliding window. *(starts typing immediately)*

> **Interviewer's note:** No questions about negatives, the size of n, or the expected output for edge cases. The candidate picked a pattern from one keyword.

**Candidate:** *(types silently for about four minutes)*

```java
static int subarraySum(int[] nums, int k) {
    int left = 0, sum = 0, count = 0;
    for (int right = 0; right < nums.length; right++) {
        sum += nums[right];
        while (sum > k && left <= right) sum -= nums[left++];
        if (sum == k) count++;
    }
    return count;
}
```

**Candidate:** Done. It's O(n).

**Interviewer:** Can you walk me through an example?

**Candidate:** For `[1, 2, 3]` and k = 3… sum is 1, then 3, so count is 1. Then 6, too big, remove 1 and 2, so 3 again, count is 2. Correct.

**Interviewer:** What about `[1, -1, 1]` with k = 1?

**Candidate:** *(long pause)* Sum is 1, count 1. Then 0. Then 1 again, count 2. So 2?

**Interviewer:** How many subarrays sum to 1 there?

**Candidate:** `[1]`, `[1]`… and `[1, -1, 1]`. Oh, three. *(silence for about a minute)* Maybe I can shrink differently… *(edits the while condition twice, both wrong)*

> **Interviewer's note:** The window only works when extending always increases the sum, which is false with negatives. The candidate didn't ask about negatives, didn't state the brute force, and when the counterexample came they patched code instead of rethinking the approach. Long silences.

**Interviewer:** We're nearly out of time. What's the complexity of what you'd do now?

**Candidate:** I'd probably check every subarray, so O(n²) I guess.

### Score

| Signal | Score (1–4) | Why |
| --- | --- | --- |
| Problem solving | 1 | Matched a keyword to a pattern; no brute force; no recovery after the counterexample |
| Coding | 2 | Code is tidy but solves a different problem |
| Verification | 1 | Traced only the happy example; the interviewer had to find the bug |
| Communication | 1 | Long silences; no narration of decisions |
| Complexity | 2 | O(n) stated without reasons; the fallback was a guess |

**Outcome: no hire.** The candidate knew sliding windows and prefix sums. They lost on process, not knowledge.

## Transcript 2: the strong candidate

**Interviewer:** *(reads the same problem)*

**Candidate:** Let me check a few things first. Can the numbers be negative? And how large can the array be?

**Interviewer:** Yes, negatives and zeros are allowed. n is up to 2 × 10⁴.

**Candidate:** And I return a count, not the subarrays themselves. Let me write an example: `[1, 2, 3]` with k = 3 should give 2, from `[1, 2]` and `[3]`. Is that right?

**Interviewer:** Yes.

> **Interviewer's note:** Clarified the two facts that decide the algorithm (negatives and n) and confirmed an example. About 90 seconds.

**Candidate:** The brute force tries every start and extends the end with a running sum. That's O(n²), 4 × 10⁸ for this n. That's borderline, so I'd like something better. My first instinct is a sliding window, but with negatives the sum doesn't grow monotonically as the window extends, so I can't decide when to shrink. That rules it out.

**Candidate:** What the brute force repeats is summing ranges. A range sum is a difference of prefix sums: `sum(i..j) = prefix[j] − prefix[i−1]`. So for each j, I need the number of earlier prefixes equal to `prefix[j] − k`. A hash map from prefix sum to count gives that in O(1). That's O(n) time and O(n) space overall. Shall I code that?

**Interviewer:** Go ahead.

> **Interviewer's note:** Stated the brute force with its cost, explicitly rejected the tempting wrong pattern with a reason, and derived the fix from the brute force's repeated work. Asked before coding.

**Candidate:** I'll seed the map with prefix 0 seen once. That's the empty prefix, so subarrays starting at index 0 are counted. I'll use a `long` for the prefix in case sums get large.

```java
static int subarraySum(int[] nums, int k) {
    Map<Long, Integer> seen = new HashMap<>();
    seen.put(0L, 1);                                   // the empty prefix: subarrays starting at index 0
    long prefix = 0; int count = 0;
    for (int x : nums) {
        prefix += x;
        count += seen.getOrDefault(prefix - k, 0);     // earlier prefixes that complete a sum of k
        seen.merge(prefix, 1, Integer::sum);           // store AFTER using it
    }
    return count;
}
```

**Candidate:** One subtle line: I add the current prefix to the map **after** looking it up. Otherwise, with k = 0, a prefix would pair with itself and count an empty subarray.

**Candidate:** Let me trace `[1, 2, 3]`, k = 3.

| x | prefix | look up prefix − k | count | map after |
| --- | --- | --- | --- | --- |
| 1 | 1 | −2 → 0 | 0 | 0:1, 1:1 |
| 2 | 3 | 0 → 1 | 1 | 0:1, 1:1, 3:1 |
| 3 | 6 | 3 → 1 | 2 | …, 6:1 |

**Candidate:** That's 2, correct. Now the edge cases. `[1, -1, 1]` with k = 1: prefixes are 1, 0, 1. The first adds 1 (from prefix 0). The third looks up prefix 0, which has been seen twice, so it adds 2. That's 3 in total: `[1]`, `[1]` and `[1, -1, 1]`. Right. `[0, 0]` with k = 0 should be 3, and the store-after rule gives exactly 3. An empty array returns 0.

> **Interviewer's note:** Traced with a table, chose edge cases that target the risky parts (negatives, k = 0), and explained a subtle line before being asked.

**Candidate:** Final complexity: O(n) time, since each element is one map lookup and one update, and O(n) space for up to n + 1 distinct prefixes. If all numbers were positive, a sliding window would do it in O(1) space.

**Interviewer:** Nice. What if I asked for the longest such subarray instead of the count?

**Candidate:** Same idea, but store the **first** index of each prefix instead of a count, and the length at j is j minus that index.

### Score

| Signal | Score (1–4) | Why |
| --- | --- | --- |
| Problem solving | 4 | Brute force → bottleneck → fix; rejected the wrong pattern with a reason |
| Coding | 4 | Correct first time, clear names, explained the subtle ordering |
| Verification | 4 | Table trace plus targeted edge cases, unprompted |
| Communication | 4 | Narrated decisions, asked before coding |
| Complexity | 4 | Time and space with reasons, plus the trade-off for positives |

**Outcome: strong hire.** It took about 25 minutes, and most of what scored was said out loud, not typed.

## Transcript 3: stuck, then recovering

> Koko has piles of bananas and `h` hours. Each hour she picks one pile and eats up to `k` bananas from it. Find the minimum `k` that lets her finish in time. (piles up to 10⁴, values up to 10⁹, `h` ≥ number of piles.)

**Candidate:** *(after clarifying)* My first thought is to sort the piles and do something greedy with the biggest ones… *(pauses)* Actually, I don't see a greedy rule that works. Let me step back and use my checklist rather than guess.

> **Interviewer's note:** Recognised the dead end quickly and said so, instead of going quiet.

**Candidate:** The brute force: try k = 1, 2, 3, and so on, and for each k compute the hours as the sum of `ceil(pile / k)`. The first k that fits is the answer. That's O(max × n), and max is 10⁹, so it's far too slow. But it's correct, and it tells me the answer is a **number** with a yes/no check… *(pause)* I feel there's a structure here I'm not using.

**Interviewer:** What happens to the hours as k grows?

**Candidate:** They can only go down or stay the same. Eating faster never takes longer. So "finishes in time" is false, false, …, then true from some k onward. It's monotonic, which means I can **binary search on k** instead of trying every value. That's the binary-search-on-the-answer pattern. Thanks, that was the missing piece.

> **Interviewer's note:** The hint was a question, not the answer. The candidate connected it to a named pattern and explained *why* it applies (monotonicity). That's the response interviewers hope for.

**Candidate:** The range is 1 to max(piles); max always works because `h` ≥ the number of piles. The check is O(n), so the total is O(n log max), about 10⁴ × 30.

```java
static int minEatingSpeed(int[] piles, int h) {
    int max = Arrays.stream(piles).max().getAsInt();
    return (int) firstTrue(1, max, k -> canFinish(piles, h, k));
}

static boolean canFinish(int[] piles, int h, long k) {
    long hours = 0;
    for (int p : piles) hours += (p + k - 1) / k;          // ceil(p / k) with integers only
    return hours <= h;
}
```

**Candidate:** `firstTrue` is my standard binary search for the first value where a condition becomes true. I'm using `long` for the hours, because 10⁴ piles of 10⁹ bananas at speed 1 overflows an `int`. Test: piles `[3, 6, 7, 11]` with h = 8. Speed 4 takes 1 + 2 + 2 + 3 = 8 hours, which fits. Speed 3 takes 1 + 2 + 3 + 4 = 10, which doesn't. So the answer is 4.

### Score

| Signal | Score (1–4) | Why |
| --- | --- | --- |
| Problem solving | 3 | Needed a hint, but used it immediately and justified the pattern |
| Coding | 4 | Reused a known template; handled overflow |
| Verification | 4 | Checked the boundary on both sides (3 fails, 4 works) |
| Communication | 4 | Said when the first idea failed; reasoned aloud through the brute force |
| Complexity | 4 | O(n log max) with numbers |

**Outcome: hire.** Needing one hint is normal. Going silent, or ignoring the hint, is what costs offers.

## What separated them

| Moment | Weak | Strong |
| --- | --- | --- |
| First minute | Started coding | Asked about negatives and n; wrote an example |
| Choosing the approach | Keyword → pattern | Brute force → what repeats → pattern, wrong options ruled out with reasons |
| Before coding | Silent | "Shall I code that?" |
| A subtle line | Not noticed | Explained (store after lookup) |
| Testing | Happy path only | Table trace + edge cases aimed at the risky logic |
| When stuck | Patched code, went quiet | Said so, fell back to the brute force, used the hint |

<Practice task="Record yourself solving a problem from your log in 40 minutes, then transcribe the first 10 minutes. Mark every place the weak candidate's habits appear. What do you look for?">

Look for these weak habits:

- Coding before asking about negatives, duplicates, n or empty input.
- No example confirmed with the interviewer.
- No brute force stated, or no complexity attached to it.
- Picking a pattern from a keyword, with no reason for rejecting the alternatives.
- Silent stretches longer than 30 seconds.
- Starting to code without saying "shall I code this?".

Most people find two or three of these the first time. Fix one per mock until they're gone.

</Practice>

<Takeaways>

- The weak and strong candidates knew the same patterns; process decided the outcome.
- Clarify the facts that change the algorithm, state the brute force with its cost, and rule out tempting wrong patterns out loud.
- Explain subtle lines before you're asked; trace with a table; test the risky edge cases.
- When stuck, say so, return to the brute force and connect the hint to a named pattern.

</Takeaways>
