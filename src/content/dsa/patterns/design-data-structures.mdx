"Design an LRU cache" is one of the most-asked interview questions there is, and it frightens people because it doesn't look like an algorithm problem. There's no array to scan and no pattern name in the statement, just a class with methods that must all run in O(1). The trick is the same every time: **no single structure does everything, so combine two**, each covering the other's weakness. Once you see that, this whole family of problems becomes a short checklist.

<Callout type="note" title="New to the core structures?">

This lesson assumes you know what each structure is fast and slow at. If not, read [Choosing a Data Structure](/dsa/data-structures/choosing-a-data-structure) in Data Structures Basics first. It has step-through visuals.

</Callout>

<Callout type="tip" title="How to spot it">

- The problem says **"Design…"** or **"Implement the class…"** and lists methods.
- Each method has a **complexity requirement**, usually "O(1) average" or "O(log n)".
- The operations pull in different directions: **find by key** *and* **keep an order**, or **delete anything** *and* **pick a random element**.
- It mentions **eviction**, **capacity**, **timestamps**, **iterators** or **streams**.

</Callout>

## The method: list the operations, then pair structures

Write each required operation next to the structure that does it fast:

| Structure | Fast at | Slow at |
| --- | --- | --- |
| `HashMap` | Find / insert / delete by key, O(1) | Any notion of order |
| Doubly linked list | Move or remove a **known** node, O(1); keep a recency order | Finding a node, O(n) |
| `ArrayList` | Access by index, add/remove **at the end**, O(1) | Removing from the middle, O(n) |
| Heap | Min/max, O(log n) | Removing an arbitrary element, O(n) |
| `TreeMap` | Floor/ceiling, ordered keys, O(log n) | Nothing major, but not O(1) |

If no single row covers every operation, pick two rows whose strengths cover each other's weaknesses, and keep them **in sync** in every method. That's the whole pattern.

## LRU cache: hash map + doubly linked list

> `get(key)` and `put(key, value)` in O(1). When the cache is full, evict the **least recently used** key.

- Find a key in O(1) → **hash map**.
- Know which key is least recent, and move a key to "most recent" in O(1) → **doubly linked list** in order of use.

The map stores **key → list node**, so after a lookup you can unlink the node directly, without searching.

Step through it: the map's arrows point straight at list nodes, a used node slides to the front, and the node at the back is the one evicted.

<LruViz examples={['lesson', 'refresh']} />

```java
static class LRUCache {
    private static class Node {
        int key, val;
        Node prev, next;
        Node(int k, int v) { key = k; val = v; }
    }
    private final int capacity;
    private final Map<Integer, Node> map = new HashMap<>();
    private final Node head = new Node(0, 0), tail = new Node(0, 0);   // sentinels: no null checks

    LRUCache(int capacity) {
        this.capacity = capacity;
        head.next = tail;
        tail.prev = head;
    }

    int get(int key) {
        Node n = map.get(key);
        if (n == null) return -1;
        remove(n);
        addFront(n);                                // used: now the most recent
        return n.val;
    }

    void put(int key, int value) {
        Node n = map.get(key);
        if (n != null) {
            n.val = value;
            remove(n);
            addFront(n);
            return;
        }
        if (map.size() == capacity) {
            Node lru = tail.prev;                   // least recently used sits before the tail
            remove(lru);
            map.remove(lru.key);                    // why the node stores its key
        }
        n = new Node(key, value);
        map.put(key, n);
        addFront(n);
    }

    private void remove(Node n) { n.prev.next = n.next; n.next.prev = n.prev; }
    private void addFront(Node n) { n.next = head.next; n.prev = head; head.next.prev = n; head.next = n; }
}
```

Three details interviewers look for:

- **Sentinel head and tail** nodes remove every "is this the first or last node?" special case.
- The node stores its **key**, because eviction starts from the list and must also delete from the map.
- **Doubly** linked, because unlinking a node needs its predecessor.

In real Java code, `LinkedHashMap` with `accessOrder = true` and an overridden `removeEldestEntry` is an LRU cache in five lines. Mention it, but expect to be asked to build the real thing.

## LFU cache: three maps and a minimum counter

> Evict the **least frequently used** key; among ties, the least recently used.

Now we need, in O(1):

- the value and use-count of a key, which takes two hash maps;
- the keys with a given count in recency order, which takes a map from **count → `LinkedHashSet`**, iterated oldest first;
- the smallest count in use, which is a single `minFreq` variable.

```java
static class LFUCache {
    private final int capacity;
    private final Map<Integer, Integer> vals = new HashMap<>(), freq = new HashMap<>();
    private final Map<Integer, LinkedHashSet<Integer>> byFreq = new HashMap<>();   // freq → keys, oldest first
    private int minFreq;

    LFUCache(int capacity) { this.capacity = capacity; }

    int get(int key) {
        if (!vals.containsKey(key)) return -1;
        touch(key);
        return vals.get(key);
    }

    void put(int key, int value) {
        if (capacity == 0) return;
        if (vals.containsKey(key)) {
            vals.put(key, value);
            touch(key);
            return;
        }
        if (vals.size() == capacity) {
            Iterator<Integer> it = byFreq.get(minFreq).iterator();
            int evict = it.next();                  // least frequent; among those, least recent
            it.remove();
            vals.remove(evict);
            freq.remove(evict);
        }
        vals.put(key, value);
        freq.put(key, 1);
        byFreq.computeIfAbsent(1, f -> new LinkedHashSet<>()).add(key);
        minFreq = 1;                                // a new key always has the lowest count
    }

    private void touch(int key) {                   // move key from bucket f to bucket f + 1
        int f = freq.get(key);
        freq.put(key, f + 1);
        LinkedHashSet<Integer> bucket = byFreq.get(f);
        bucket.remove(key);
        if (bucket.isEmpty() && f == minFreq) minFreq++;
        byFreq.computeIfAbsent(f + 1, x -> new LinkedHashSet<>()).add(key);
    }
}
```

Why `minFreq` never needs a search:

- It only changes in two ways. A new key resets it to 1.
- Touching a key moves it from count f to f + 1. If that empties the bucket for the minimum, the new minimum is exactly f + 1.

## Insert, delete, get random, all in O(1)

- A hash set can't pick a random element in O(1).
- An array can, but deleting from its middle is O(n).
- **Combine them**: an `ArrayList` of values plus a map **value → index**.
- To delete, **move the last element into the hole**, then remove the end.

```java
static class RandomizedSet {
    private final List<Integer> items = new ArrayList<>();
    private final Map<Integer, Integer> index = new HashMap<>();   // value → its position in items
    private final Random random = new Random();

    boolean insert(int val) {
        if (index.containsKey(val)) return false;
        index.put(val, items.size());
        items.add(val);
        return true;
    }

    boolean remove(int val) {
        Integer i = index.get(val);
        if (i == null) return false;
        int last = items.get(items.size() - 1);
        items.set(i, last);                         // move the last element into the hole
        index.put(last, i);
        items.remove(items.size() - 1);             // removing the end is O(1)
        index.remove(val);
        return true;
    }

    int getRandom() { return items.get(random.nextInt(items.size())); }
}
```

The order of the two `index` updates matters when `val` *is* the last element. Writing `index.put(last, i)` first and `index.remove(val)` second handles that case correctly. The tests in the reference solution cover it.

## Time-based key-value store: map + sorted list

> `set(key, value, timestamp)`; `get(key, timestamp)` returns the value with the largest timestamp **≤ the given one**.

Timestamps arrive in increasing order, so each key's list of timestamps is already sorted. A `get` is a [binary search](/dsa/patterns/binary-search) for the last timestamp that isn't too big:

```java
static class TimeMap {
    private final Map<String, List<Integer>> times = new HashMap<>();
    private final Map<String, List<String>> values = new HashMap<>();

    /** Timestamps for a key arrive in increasing order, so each list stays sorted. */
    void set(String key, String value, int timestamp) {
        times.computeIfAbsent(key, k -> new ArrayList<>()).add(timestamp);
        values.computeIfAbsent(key, k -> new ArrayList<>()).add(value);
    }

    /** The value with the largest timestamp ≤ the given one, or "". */
    String get(String key, int timestamp) {
        List<Integer> ts = times.get(key);
        if (ts == null) return "";
        int lo = 0, hi = ts.size();                 // first index with ts > timestamp
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (ts.get(mid) > timestamp) hi = mid; else lo = mid + 1;
        }
        return lo == 0 ? "" : values.get(key).get(lo - 1);
    }
}
```

If timestamps could arrive out of order, use `Map<String, TreeMap<Integer, String>>` and `floorEntry(timestamp)`. That costs O(log n) per `set` too, and it's a good follow-up to mention.

## Iterators: hold the next element

Iterator problems all ask you to compute **lazily**: produce the next element only when asked. The trick is to keep **one element of look-ahead** (or a stack of positions) inside the object.

**Peeking iterator.** Pre-fetch one element so `peek()` can return it without consuming it:

```java
static class PeekingIterator<T> implements Iterator<T> {
    private final Iterator<T> it;
    private T next;
    private boolean hasNext;

    PeekingIterator(Iterator<T> it) { this.it = it; advance(); }

    T peek() { return next; }
    @Override public boolean hasNext() { return hasNext; }
    @Override public T next() {
        if (!hasNext) throw new NoSuchElementException();
        T r = next;
        advance();
        return r;
    }
    private void advance() { hasNext = it.hasNext(); next = hasNext ? it.next() : null; }
}
```

**Flatten a nested list** like `[1, [2, [3]], 4]` without flattening it up front. Keep a **stack of iterators**, one per open list. That is iterative DFS, done one element at a time:

```java
static class NestedIterator implements Iterator<Integer> {
    private final Deque<Iterator<Object>> stack = new ArrayDeque<>();
    private Integer next;

    NestedIterator(List<Object> list) { stack.push(list.iterator()); }

    @Override public boolean hasNext() {
        while (next == null && !stack.isEmpty()) {
            Iterator<Object> top = stack.peek();
            if (!top.hasNext()) { stack.pop(); continue; }          // this list is finished
            Object o = top.next();
            if (o instanceof Integer i) next = i;
            else {
                @SuppressWarnings("unchecked") List<Object> inner = (List<Object>) o;
                stack.push(inner.iterator());                     // descend into the inner list
            }
        }
        return next != null;
    }

    @Override public Integer next() {
        if (!hasNext()) throw new NoSuchElementException();
        Integer r = next;
        next = null;
        return r;
    }
}
```

`hasNext()` does the work and must be **safe to call twice**: it only searches when nothing is buffered. Empty inner lists such as `[[], [[]]]` are the classic test, and the loop skips them naturally.

## Designing with a heap: lazy deletion

Many design questions boil down to *"keep giving me the smallest (or largest) thing, while things keep changing"*: the lowest free seat, the highest-rated dish, the smallest index holding a number, the max price after corrections. A heap (`PriorityQueue`) answers "smallest" in O(1) and adds in O(log n). The trouble is **changing or deleting** something that isn't on top: `PriorityQueue.remove(x)` searches the whole heap, O(n).

Three ways around it:

1. **Lazy deletion.** Keep a map as the source of truth. On every change, update the map and push a **new** heap entry; leave the old entry where it is. When you read the top, first pop entries that disagree with the map ("stale"). Every entry is pushed once and popped at most once, so it's **O(log n) amortised** per operation.
2. **A sorted set** (`TreeSet` / `TreeMap`) instead of a heap: `remove(x)` is O(log n), and `first()` / `last()` give the min and max. Good when values are unique, or when you need both ends or neighbours (Exam Room).
3. **Don't store what you can compute.** If most of the items are "everything from `next` upwards", keep only a counter for them and a small heap for the exceptions (Seat Reservation Manager, Smallest Number in Infinite Set).

### Stock Price Fluctuation (2034): lazy deletion

Prices arrive with timestamps, out of order, and a later record can **correct** an earlier timestamp. `current` needs the latest timestamp's price; `maximum` and `minimum` need the extremes over the corrected prices.

```java
class StockPrice {
    private final Map<Integer, Integer> price = new HashMap<>();                              // the truth
    private final PriorityQueue<int[]> maxH = new PriorityQueue<>((a, b) -> b[0] - a[0]);   // {price, timestamp}
    private final PriorityQueue<int[]> minH = new PriorityQueue<>((a, b) -> a[0] - b[0]);
    private int latest = 0;

    public void update(int timestamp, int p) {
        price.put(timestamp, p);
        latest = Math.max(latest, timestamp);
        maxH.add(new int[] { p, timestamp });         // the old entry for this timestamp just goes stale
        minH.add(new int[] { p, timestamp });
    }

    public int current() { return price.get(latest); }
    public int maximum() { return top(maxH); }
    public int minimum() { return top(minH); }

    private int top(PriorityQueue<int[]> h) {
        while (price.get(h.peek()[1]) != h.peek()[0]) h.poll();   // stale: that timestamp was corrected
        return h.peek()[0];
    }
}
```

### Design a Number Container System (2349): a lazy heap per key

`change(index, number)` puts `number` at `index` (replacing what was there); `find(number)` returns the smallest index holding `number`. Keep `index → number` as the truth and a min-heap of indexes per number. An index in `number`'s heap is stale if that index now holds something else.

```java
class NumberContainers {
    private final Map<Integer, Integer> at = new HashMap<>();                     // index → number
    private final Map<Integer, PriorityQueue<Integer>> where = new HashMap<>();   // number → indexes (some stale)

    public void change(int index, int number) {
        at.put(index, number);
        where.computeIfAbsent(number, x -> new PriorityQueue<>()).add(index);
    }

    public int find(int number) {
        PriorityQueue<Integer> h = where.get(number);
        if (h == null) return -1;
        while (!h.isEmpty() && at.get(h.peek()) != number) h.poll();   // that index holds something else now
        return h.isEmpty() ? -1 : h.peek();
    }
}
```

### Design a Food Rating System (2353): a heap per group, with tie-breaks

`highestRated(cuisine)` returns the best-rated food of that cuisine (alphabetically first on a tie), and ratings change. Same recipe: a map `food → rating` is the truth, and each cuisine has a heap ordered by rating, then name. An entry is stale when its rating isn't the food's current rating.

```java
class FoodRatings {
    private record Entry(int rating, String food) {}
    private final Map<String, Integer> rating = new HashMap<>();
    private final Map<String, String> cuisineOf = new HashMap<>();
    private final Map<String, PriorityQueue<Entry>> best = new HashMap<>();

    public FoodRatings(String[] foods, String[] cuisines, int[] ratings) {
        for (int i = 0; i < foods.length; i++) {
            cuisineOf.put(foods[i], cuisines[i]);
            best.computeIfAbsent(cuisines[i], c -> new PriorityQueue<>(
                (a, b) -> a.rating() != b.rating() ? Integer.compare(b.rating(), a.rating()) : a.food().compareTo(b.food())));
            changeRating(foods[i], ratings[i]);
        }
    }

    public void changeRating(String food, int newRating) {
        rating.put(food, newRating);
        best.get(cuisineOf.get(food)).add(new Entry(newRating, food));
    }

    public String highestRated(String cuisine) {
        PriorityQueue<Entry> h = best.get(cuisine);
        while (h.peek().rating() != rating.get(h.peek().food())) h.poll();   // an old rating
        return h.peek().food();
    }
}
```

### Seat Reservation Manager (1845) and Smallest Number in Infinite Set (2336): a counter plus a heap

Seats `1 … n` start free, and `reserve` must hand out the **lowest** free seat. Putting all n seats in a heap up front costs O(n log n) (or O(n) with heapify). But until a seat is returned, the free seats are exactly "`next` and everything after it". So keep a counter `next` and a min-heap holding only the seats that were **given back**.

```java
class SeatManager {
    private final PriorityQueue<Integer> returned = new PriorityQueue<>();   // freed seats below next
    private int next = 1;                                                  // seats ≥ next were never reserved

    public SeatManager(int n) {}
    public int reserve() { return returned.isEmpty() ? next++ : returned.poll(); }
    public void unreserve(int seatNumber) { returned.add(seatNumber); }
}
```

Smallest Number in Infinite Set is the same design, with one catch: `addBack(x)` may add a number that is **already** in the set. Use a structure that ignores duplicates: a `TreeSet`, or a heap plus a `HashSet` of what's in it.

```java
class SmallestInfiniteSet {
    private int next = 1;                                     // every number ≥ next is in the set
    private final TreeSet<Integer> added = new TreeSet<>();   // numbers < next that were added back

    public int popSmallest() { return added.isEmpty() ? next++ : added.pollFirst(); }
    public void addBack(int num) { if (num < next) added.add(num); }   // ≥ next is already in; the set ignores repeats
}
```

### Exam Room (855): a sorted set of who's seated

A student takes the seat that **maximises the distance** to the nearest student (lowest seat on a tie); students also leave. With up to 10⁹ seats you store only the seated positions, in a `TreeSet`. The best seat is either seat 0, seat n − 1, or the middle of the widest gap between two neighbours, so one pass over the sorted positions finds it.

```java
class ExamRoom {
    private final int n;
    private final TreeSet<Integer> seated = new TreeSet<>();

    public ExamRoom(int n) { this.n = n; }

    public int seat() {
        if (seated.isEmpty()) { seated.add(0); return 0; }
        int bestSeat = 0, bestDist = seated.first();         // seat 0: the distance to the first student
        Integer prev = null;
        for (int s : seated) {
            if (prev != null && (s - prev) / 2 > bestDist) { bestDist = (s - prev) / 2; bestSeat = prev + bestDist; }
            prev = s;
        }
        if (n - 1 - seated.last() > bestDist) bestSeat = n - 1;   // seat n − 1
        seated.add(bestSeat);
        return bestSeat;
    }

    public void leave(int p) { seated.remove(p); }
}
```

`seat` is O(k) for k seated students, fine for 10⁴ calls. The O(log n) version keeps the **gaps** in a heap (widest first, then lowest seat) with lazy deletion: `leave` merges two gaps into one, and the two old gaps go stale. The Solution tab has it.

## Designing with queues

A queue is the right structure when **order of arrival is the rule**: first come, first served, or "drop whatever is oldest". Most queue design questions add one twist to that rule: a sliding time window, a middle you can reach, an element that jumps to the back, someone leaving the line early, or several threads sharing it. Each twist has a standard answer.

| Twist | Structure | Problem |
| --- | --- | --- |
| Drop what is too old | Queue; expire from the front | Number of Recent Calls (933) |
| Reach the middle | Two deques, kept balanced | Design Front Middle Back Queue (1670) |
| Move the k-th to the back | Fenwick tree over growing positions | Design Most Recently Used Queue (1756) |
| Leave the line early | Queue + set, lazy deletion | Design Ride Sharing System |
| Many threads | Lock + two condition variables | Design Bounded Blocking Queue (1188) |

### Number of Recent Calls (933): expire from the front

`ping(t)` records a request at time `t` (always larger than the last one) and returns how many requests fall in `[t − 3000, t]`. Times only grow, so a request that leaves the window never comes back: append on the right, drop from the left.

```java
class RecentCounter {
    private final ArrayDeque<Integer> q = new ArrayDeque<>();

    public int ping(int t) {
        q.offerLast(t);
        while (q.peekFirst() < t - 3000) q.pollFirst();   // too old, gone for good
        return q.size();
    }
}
```

Each request is added once and removed once: O(1) amortised. The same shape (a queue of timestamps) is the sliding-window rate limiter in system design.

### Design Front Middle Back Queue (1670): two balanced halves

Push and pop at the front, the **middle** and the back; with two middles, use the front one. A single list makes the middle O(n). Instead split the queue into `left` and `right` deques and keep `right` the same size as `left` or **one bigger**. Then the middle is always at the boundary:

- `pushMiddle`: equal halves → front of `right`; otherwise → back of `left`.
- `popMiddle`: equal halves → back of `left` (the frontmost middle); otherwise → front of `right`.
- After any front or back operation, move at most one element across to restore the sizes.

```java
class FrontMiddleBackQueue {
    private final ArrayDeque<Integer> left = new ArrayDeque<>(), right = new ArrayDeque<>();

    private void fix() {   // right.size() == left.size() or left.size() + 1
        if (left.size() > right.size()) right.offerFirst(left.pollLast());
        else if (right.size() > left.size() + 1) left.offerLast(right.pollFirst());
    }
    public void pushFront(int val) { left.offerFirst(val); fix(); }
    public void pushMiddle(int val) {
        if (left.size() == right.size()) right.offerFirst(val); else left.offerLast(val);
    }
    public void pushBack(int val) { right.offerLast(val); fix(); }
    public int popFront() {
        if (right.isEmpty()) return -1;                     // right empty ⇒ whole queue empty
        int v = left.isEmpty() ? right.pollFirst() : left.pollFirst();
        fix();
        return v;
    }
    public int popMiddle() {
        if (right.isEmpty()) return -1;
        return left.size() == right.size() ? left.pollLast() : right.pollFirst();
    }
    public int popBack() {
        if (right.isEmpty()) return -1;
        int v = right.pollLast();
        fix();
        return v;
    }
}
```

The same "two halves, balanced" idea is behind the running median ([Heaps](/dsa/patterns/heap-patterns)), with heaps instead of deques.

### Design Most Recently Used Queue (1756): positions that only grow

`MRUQueue(n)` starts as `[1 … n]`; `fetch(k)` moves the k-th element to the end. A list (`remove(k − 1)`, then `add`) is O(n) per fetch and passes; the follow-up asks for better.

The trick: never move anything. Give every element a **position** that only grows, 1 … n at the start, and the next free position past the end each time it is fetched. A [Fenwick tree](/dsa/patterns/range-queries) marks which positions are occupied, so "the k-th element" is "the k-th occupied position", found in O(log n) by walking down the powers of two:

```java
public int fetch(int k) {
    int pos = 0;
    for (int step = Integer.highestOneBit(cap); step > 0; step >>= 1)
        if (pos + step <= cap && bit[pos + step] < k) { pos += step; k -= bit[pos]; }
    pos++;                       // the k-th occupied position
    int v = val[pos];
    add(pos, -1);                // free it...
    val[++end] = v;              // ...and write the value at a new position at the back
    add(end, 1);
    return v;
}
```

Square-root decomposition (blocks of about √n elements, skip whole blocks when counting to k) is the other standard answer, at O(√n) per fetch.

### Design Ride Sharing System: leaving the line early

Riders and drivers each wait in arrival order; a match pairs the longest-waiting driver with the longest-waiting rider and returns `[driverId, riderId]` (or `[-1, -1]`). A rider may **cancel** while waiting. Removing from the middle of a queue is O(n), so don't: keep a set of riders still waiting, remove the id from the set on cancel, and skip queue fronts that are no longer in the set when matching. This is the same **lazy deletion** as the heaps above, on a queue.

```java
class RideSharingSystem {
    private final ArrayDeque<Integer> riders = new ArrayDeque<>(), drivers = new ArrayDeque<>();
    private final Set<Integer> waiting = new HashSet<>();

    public void addRider(int riderId) { riders.offerLast(riderId); waiting.add(riderId); }
    public void addDriver(int driverId) { drivers.offerLast(driverId); }
    public void cancelRider(int riderId) { waiting.remove(riderId); }   // no-op if already matched

    public int[] matchDriverWithRider() {
        while (!riders.isEmpty() && !waiting.contains(riders.peekFirst())) riders.pollFirst();   // cancelled
        if (riders.isEmpty() || drivers.isEmpty()) return new int[] { -1, -1 };
        int r = riders.pollFirst();
        waiting.remove(r);
        return new int[] { drivers.pollFirst(), r };
    }
}
```

### Design Bounded Blocking Queue (1188): producers and consumers

The concurrency version: `enqueue` must **wait** while the queue is full, and `dequeue` must wait while it is empty, with many threads calling at once. Three rules:

1. **One lock guards everything.** Every method, `size` included, reads or writes shared state.
2. **Waiting releases the lock.** A thread that slept while holding it would stop everyone else from making room. Condition variables do this: `await()` releases the lock and re-acquires it on waking.
3. **Wait in a `while`, not an `if`.** A woken thread may find the condition false again (another thread got there first, or a spurious wake-up).

Use **two** conditions so a signal reaches a thread that can use it: producers wait on `notFull`, consumers on `notEmpty`.

```java
class BoundedBlockingQueue {
    private final int capacity;
    private final ArrayDeque<Integer> q = new ArrayDeque<>();
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition(), notEmpty = lock.newCondition();

    public BoundedBlockingQueue(int capacity) { this.capacity = capacity; }

    public void enqueue(int element) throws InterruptedException {
        lock.lock();
        try {
            while (q.size() == capacity) notFull.await();   // releases the lock while waiting
            q.offerLast(element);
            notEmpty.signal();                              // one consumer can go now
        } finally { lock.unlock(); }
    }

    public int dequeue() throws InterruptedException {
        lock.lock();
        try {
            while (q.isEmpty()) notEmpty.await();
            int v = q.pollFirst();
            notFull.signal();                               // one producer can go now
            return v;
        } finally { lock.unlock(); }
    }

    public int size() {
        lock.lock();
        try { return q.size(); } finally { lock.unlock(); }
    }
}
```

`synchronized` methods with `wait()` / `notifyAll()` also work, but every change wakes producers and consumers alike. Two semaphores (free slots, filled slots) plus a mutex is the other classic answer. In C++ this is `mutex` + `condition_variable`, in Python `threading.Condition`.

<Callout type="note" title="How it is judged here">

The solver runs your class on one thread, so its tests never call `enqueue` on a full queue or `dequeue` on an empty one (that would wait forever). They check the queue's behaviour and capacity; the waiting itself is yours to get right. Write it exactly as you would for the concurrent version.

</Callout>

### Time Needed to Buy Tickets (2073): count instead of simulating

Some "queue" problems describe a line of people and invite you to simulate it. Often the rotation doesn't change the answer, and counting does the same work in one pass.

Here, each second the front person buys one ticket and rejoins the back if they need more. Person `k` finishes after `tickets[k]` rounds; in those rounds everyone at or before `k` buys up to their own need, and everyone after `k` gets one round fewer:

```java
int t = 0;
for (int i = 0; i < tickets.length; i++)
    t += Math.min(tickets[i], i <= k ? tickets[k] : tickets[k] - 1);
return t;
```

### Number of Students Unable to Eat Lunch (1700): only the counts matter

A student who doesn't want the top sandwich walks to the back, so the top sandwich is taken as long as **anyone** still in line wants it. Only the counts matter: walk the sandwiches, and the first one nobody wants stops everything.

```java
int[] want = new int[2];
for (int s : students) want[s]++;
for (int i = 0; i < sandwiches.length; i++) {
    if (want[sandwiches[i]] == 0) return sandwiches.length - i;   // everyone left goes hungry
    want[sandwiches[i]]--;
}
return 0;
```

### Number of People Aware of a Secret (2327): a queue of cohorts

Here the queue is of **cohorts**: `learned[d]` people learn on day `d`; they share from day `d + delay` and forget on day `d + forget`. The number of people sharing on day `d` is a sliding window sum: add the cohort that starts sharing, subtract the one that forgets.

```java
learned[1] = 1;
long sharing = 0;
for (int d = 2; d <= n; d++) {
    if (d - delay >= 1) sharing = (sharing + learned[d - delay]) % MOD;          // starts sharing today
    if (d - forget >= 1) sharing = (sharing - learned[d - forget] + MOD) % MOD;  // forgot today
    learned[d] = sharing;                                                        // each sharer tells one person
}
// answer: learned[n − forget + 1] + … + learned[n]
```

[Dota2 Senate](/dsa/patterns/greedy) is the counter-example: there the order of the queue decides who bans whom, so you do simulate it, with two queues of indexes.

## Design problems at a glance

| Problem | Structures | Key trick |
| --- | --- | --- |
| LRU cache | HashMap + doubly linked list | Map to the node; sentinels; node stores its key |
| LFU cache | 2 maps + count → LinkedHashSet | `minFreq` only resets to 1 or moves up by one |
| Insert/delete/getRandom O(1) | ArrayList + value → index map | Swap with the last, then remove the end |
| Time-based store | Map + sorted list per key | Binary search for the last timestamp ≤ t |
| Min stack | Stack of (value, min so far) | Each entry remembers the min below it ([Stack Patterns](/dsa/patterns/stack-patterns)) |
| Queue with two stacks | In-stack + out-stack | Refill out only when empty: amortised O(1) |
| Running median | Max-heap + min-heap | Balance sizes ([Heaps](/dsa/patterns/heap-patterns)) |
| Min / max with updates | Heap + map of current values | Lazy deletion: skip stale tops |
| Lowest free seat / number | Counter + heap of returned ones | Don't store "everything from next on" |
| Middle of a queue | Two deques, balanced | The middle sits at the boundary; move one element to rebalance |
| Leave a queue early | Queue + set of who is still waiting | Lazy deletion: skip cancelled fronts |
| Blocking queue | Lock + notFull / notEmpty conditions | Wait in a `while`; waiting releases the lock |
| Max / min queue | Queue + monotonic deque | Drop values a newer one beats ([Monotonic Stack](/dsa/patterns/monotonic-stack#min-queue-and-max-queue)) |
| Iterators | One-element buffer or stack of iterators | Compute lazily; `hasNext` is idempotent |

<Callout type="warning" title="Common mistakes">

- **Updating one structure but not the other**: every method must keep both in sync. Check each method against each structure.
- **Forgetting to move on `get`**: in an LRU cache, a read counts as a use.
- **Singly linked list for LRU**: unlinking needs the previous node.
- **Removing from the middle of an ArrayList** (O(n)) instead of swapping with the last.
- **`hasNext()` with side effects** that break when it's called twice.
- **Capacity 0** in caches: `put` must do nothing.
- **`PriorityQueue.remove(x)` in a loop**: it's O(n). Use lazy deletion or a `TreeSet`.
- **Comparing boxed `Integer`s with `==`**: `map.get(a) == map.get(b)` compares references and fails above 127. Unbox one side (compare with an `int`) or use `.equals`.

</Callout>

## Interview questions

<QA q="Why does an LRU cache need both a hash map and a doubly linked list?">
The cache needs two things in O(1): finding the entry for a key, and knowing and updating the order of use so it can evict the least recently used entry. A hash map finds keys in O(1) but has no order. A doubly linked list keeps the order and can move or remove a known node in O(1), but finding a node in it is O(n). Storing key to list node in the map gives both: look the node up in the map, then unlink and move it in the list. The list must be doubly linked because unlinking needs the previous node.
</QA>

<QA q="How do you remove an arbitrary element from an array-backed set in O(1)?">
Keep a map from value to index. To remove a value, look up its index, copy the last element into that slot, update the moved element's index in the map, then remove the last slot, which is O(1). Order isn't preserved, which is fine for a set. This is what makes insert, delete and getRandom all O(1): getRandom picks a random index into the array.
</QA>

<Practice task="Design a hit counter: hit(timestamp) records a hit, and getHits(timestamp) returns the number of hits in the past 300 seconds. Timestamps are non-decreasing. What structure, and what if there are millions of hits per second?">

**Basic:** a queue of timestamps. `hit` appends; `getHits` pops from the front while the front is 300 or more seconds older than `timestamp`, then returns the size. That's amortised O(1), since each hit is popped once.

**Many hits per second:** store `(timestamp, count)` pairs, merging repeated timestamps. Or use a fixed circular array of 300 buckets indexed by `timestamp % 300`, where each bucket holds its timestamp and count; reset a bucket when its stored timestamp is stale. `getHits` sums the 300 buckets whose timestamps are recent. That's O(300) and fixed memory, however many hits arrive.

</Practice>

<Practice task="Design a data structure with inc(key), dec(key), getMaxKey() and getMinKey(), all in O(1). Which structures, and how do they connect?">

This is the "All O(1)" problem, LFU's cousin. Keep a **doubly linked list of count buckets** in increasing order of count, each bucket holding a set of keys. Also keep a map **key → its bucket**.

- `inc` moves a key to the next bucket, creating a bucket with count + 1 right after the current one if it doesn't exist. `dec` does the same in the other direction.
- Delete a bucket when it becomes empty.
- The min key is any key in the first bucket and the max key is any key in the last.

Every step is a map lookup or a neighbour-pointer change, so everything is O(1).

</Practice>

<Takeaways>

- Design problems = list the operations, then combine two structures whose strengths cover each other.
- LRU: hash map to doubly linked list nodes, sentinels, node stores its key.
- LFU: count to LinkedHashSet buckets plus a `minFreq` that only resets or steps up.
- O(1) delete from an array: swap with the last element and update the index map.
- Iterators compute lazily: buffer one element or keep a stack of iterators; `hasNext` must be safe to repeat.

</Takeaways>
