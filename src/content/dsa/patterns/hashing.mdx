A huge share of "slow" solutions have the same shape: for each element, loop over the others to find something. That inner loop is a **search** — and a hash map or hash set turns any search for an exact value into a single O(1) step. It's the simplest pattern in this track and the one you'll use most, usually as a building block inside other patterns.

<Callout type="note" title="New to hash tables?">

This lesson assumes you know how a hash map finds a key in O(1), and what collisions are. If not, read [Hash Tables](/dsa/data-structures/hash-tables) in Data Structures Basics first. It has step-through visuals.

</Callout>

<Callout type="tip" title="How to spot it">

- You're looking for a **pair** or **partner** with some property ("two numbers that sum to…", "a matching…").
- You need to know **whether you've seen** something before (duplicates, cycles, visited states).
- You need **counts** or **frequencies** (anagrams, majority, most common).
- You need to **group** items that share a property (same letters, same pattern).
- The input is **unsorted**, the constraints want O(n), and your brute force is a nested loop.

</Callout>

## The idea: remember what you've seen

A nested loop asks, for every element, "is there a partner somewhere else?" — re-scanning the array each time. Instead, walk once and **store** what you've passed in a hash map. Now "is the partner there?" is one lookup.

Step through it below. Each number takes two steps: first **check** the map for its partner (`need = target − x`), then **store** the number so later numbers can find it. Watch the map grow under the array. The second example shows why the check has to come before the store.

<TwoSumMapViz examples={['basic', 'self']} />

The trade-off is explicit: **O(n) extra memory to save O(n) time per element**. In interviews that trade is almost always worth it — say it out loud.

## The template: check, then store

```java
Map<Integer, Integer> seen = new HashMap<>();        // what you've passed → whatever you need later (index, count…)
for (int i = 0; i < nums.length; i++) {
    int partner = /* the value that would complete the answer with nums[i] */;
    if (seen.containsKey(partner)) {
        // found it — use seen.get(partner) and i
    }
    seen.put(nums[i], i);                            // store AFTER checking
}
```

Checking **before** storing matters: it stops an element from pairing with itself (in Two Sum with target 6, the single element 3 must not match itself).

## Worked problems

### Two Sum

> Return the indexes of two numbers that add up to `target`.

```java
static int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> seen = new HashMap<>();          // value → index
    for (int i = 0; i < nums.length; i++) {
        Integer j = seen.get(target - nums[i]);            // the partner we need
        if (j != null) return new int[] { j, i };
        seen.put(nums[i], i);
    }
    return new int[0];
}
```

O(n) time, O(n) space. (If the array were **sorted**, [two pointers](/dsa/patterns/two-pointers) would do it in O(1) space.)

### Contains Duplicate

```java
static boolean containsDuplicate(int[] nums) {
    Set<Integer> seen = new HashSet<>();
    for (int x : nums) if (!seen.add(x)) return true;      // add() returns false if x was already there
    return false;
}
```

### Valid Anagram — counting with an array

When the keys are small and known (26 lowercase letters), an `int[]` is a faster, simpler "hash map":

```java
static boolean isAnagram(String s, String t) {
    if (s.length() != t.length()) return false;
    int[] count = new int[26];
    for (int i = 0; i < s.length(); i++) {
        count[s.charAt(i) - 'a']++;                        // letters of s add
        count[t.charAt(i) - 'a']--;                        // letters of t cancel them
    }
    for (int c : count) if (c != 0) return false;
    return true;
}
```

### Group Anagrams — choosing the key

The art in grouping problems is the **key**: two items belong together exactly when their keys are equal. For anagrams, sorting the letters works (O(k log k) per word), but the **letter counts** are a cheaper key (O(k)):

```java
static List<List<String>> groupAnagrams(String[] words) {
    Map<String, List<String>> groups = new HashMap<>();
    for (String w : words) {
        int[] count = new int[26];
        for (char c : w.toCharArray()) count[c - 'a']++;
        String key = Arrays.toString(count);                // "[1, 0, 0, …]" — same for all anagrams
        groups.computeIfAbsent(key, k -> new ArrayList<>()).add(w);
    }
    return new ArrayList<>(groups.values());
}
```

Why convert to a `String`? Because `int[]` uses **identity** for `equals`/`hashCode` — two arrays with the same contents are different keys. Use a `String` or a `List<Integer>` as the key instead.

### Longest Consecutive Sequence — the "start of a run" trick

> Given an unsorted array, find the length of the longest run of consecutive integers (e.g. `[100, 4, 200, 1, 3, 2]` → 4, from 1, 2, 3, 4). Must be O(n).

Sorting would be O(n log n). With a set, the trick is to only start counting at numbers that **begin** a run — those whose predecessor `x − 1` isn't present. Each run is then walked exactly once:

```java
static int longestConsecutive(int[] nums) {
    Set<Integer> set = new HashSet<>();
    for (int x : nums) set.add(x);
    int best = 0;
    for (int x : set) {
        if (set.contains(x - 1)) continue;                 // not the start of a run: skip
        int len = 1;
        while (set.contains(x + len)) len++;               // walk this run once
        best = Math.max(best, len);
    }
    return best;
}
```

The `while` looks like a nested loop, but each number is visited by it at most once across the whole run — O(n) total. (Iterate the **set**, not the array, so duplicates don't trigger repeated walks.)

Step through it. A value whose predecessor is present is skipped at once; only the start of a run walks upwards. Keep an eye on the lookup counter: it never goes above about two per value.

### First Unique Character

Two passes: count everything, then find the first index whose count is 1. Counting first and deciding second is a common shape.

```java
static int firstUniqChar(String s) {
    int[] count = new int[26];
    for (char c : s.toCharArray()) count[c - 'a']++;
    for (int i = 0; i < s.length(); i++) if (count[s.charAt(i) - 'a'] == 1) return i;
    return -1;
}
```

## Variations at a glance

| Variation | Map holds | Example |
| --- | --- | --- |
| Complement lookup | value → index | Two Sum |
| Seen-before | set of values or states | Contains Duplicate, cycle detection |
| Frequency count | value → count | Valid Anagram, majority element |
| Grouping | key → list of items | Group Anagrams |
| Membership walk | set, walk from run starts | Longest Consecutive Sequence |
| Running state → first position | prefix value → earliest index | Subarray sums ([Prefix Sums](/dsa/patterns/prefix-sums)) |

<Callout type="warning" title="Common mistakes">

- **Storing before checking** — lets an element pair with itself.
- **Using `int[]` as a map key** — arrays compare by identity. Convert to `String` or `List<Integer>`.
- **Comparing `Integer` values with `==`** — fails above 127. Unbox or use `equals`.
- **Forgetting the space cost** — say "O(n) extra space"; if the interviewer wants O(1), think sorting + two pointers.
- **Assuming O(1) is guaranteed** — hash operations are O(1) *on average*; say "average".

</Callout>

## Interview questions

<QA q="When would you avoid a hash map even though it makes the solution O(n)?">
When extra memory is restricted (the interviewer asks for O(1) space), when the input is already sorted (two pointers or binary search need no extra memory), when the key space is small and known (a plain array of counts is faster and simpler), or when you need ordering such as the nearest key (use a TreeMap). Also mention that hash operations are O(1) only on average.
</QA>

<QA q="Why is the longest-consecutive-sequence solution O(n) despite the inner while loop?">
The while loop only runs from numbers that start a run (their predecessor is absent). Each number belongs to exactly one run and is stepped over once by the walk from that run's start, so the inner loop does at most n steps in total across all iterations. The outer loop is n iterations, so the whole algorithm is O(n).
</QA>

<Practice task="Given a list of email addresses, find which ones appear more than once, ignoring case. Describe the key you'd use and the data structure.">

Normalise each address to a canonical **key** — `email.toLowerCase()` (and, if the rules say so, strip dots or "+tags" in the local part). Count keys with a `HashMap<String, Integer>` using `merge`, then return keys with count above 1. O(total characters) time. The lesson's general point: the hard part of grouping problems is defining the key so that "belong together" ⇔ "equal keys".

</Practice>

<Practice task="Spot the pattern: 'Given a string and a dictionary of words, is the string a permutation of any dictionary word?' What would you precompute?">

Anagram detection is "same letter counts", so precompute a **set of keys** (sorted letters or count-strings) for every dictionary word. Then compute the key of the input string and check membership in O(k). It's Group Anagrams in disguise: precompute keys once, answer each query with one lookup.

</Practice>

<Takeaways>

- A hash map or set turns "search for a value" into one O(1) average step — the fix for most nested-loop brute forces.
- Template: walk once, **check** for what you need, then **store** what you've seen.
- Grouping problems are about choosing the key; don't use `int[]` as a key.
- Use `int[26]` for letter counts; iterate the set (not the array) when duplicates would repeat work.
- State the trade: O(n) extra space for O(n) time.

</Takeaways>
